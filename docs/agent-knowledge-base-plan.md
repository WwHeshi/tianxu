# 天序八字 Agent 与知识库建设计划

- 状态：草案
- 日期：2026-07-31
- 范围：在现有确定性排盘能力之上建设资料库、检索、命理解读与连续追问系统

## 1. 项目目标

在现有确定性排盘引擎之上，增加一个能够引用命理资料、解释命盘并支持连续追问的 Agent 系统。

系统必须做到：

- 四柱、真太阳时、大运、流年等计算只由现有后端引擎完成。
- Agent 不得重新计算或修改命盘。
- 命理判断尽量提供原文或注解依据。
- 一级原文和二级注解明确区分。
- 不同书籍、流派存在冲突时主动展示分歧。
- 每次分析可以追溯到命盘版本、资料版本、模型和提示词版本。
- 将命理内容表述为传统文化解释，而不是科学事实或确定性预测。

## 2. 总体架构

```text
                    离线资料建设
书籍/影印本
  -> 版权与版本审核
  -> OCR、录入与人工校对
  -> 原文切分
  -> 注解关联
  -> 规则卡片整理
  -> 检索索引

                    在线分析流程
用户出生信息
  -> 确定性排盘引擎
  -> 版本化命盘 JSON
  -> 问题与主题规划
  -> 一级资料检索
  -> 二级资料检索
  -> 合并、去重、重排、冲突标记
  -> 命理解读 Agent
  -> 命盘一致性与引用校验
  -> SSE 流式回答
```

系统由四类模块组成：

1. 确定性排盘引擎。
2. 知识库与检索服务。
3. 命理解读 Agent。
4. 校验与安全模块。

## 3. Agent 架构决策

### 3.1 MVP 不采用自由式多 Agent

第一版只保留一个真正负责推理的“命理解读 Agent”。它可以调用：

- 命盘读取工具。
- 知识检索工具。
- 引用读取工具。
- 会话上下文工具。

检索服务先作为普通后端模块，不需要独立 Agent。这样可以减少：

- 多 Agent 之间的上下文丢失。
- 相互放大的幻觉。
- 延迟和模型费用。
- 编排、重试和状态管理复杂度。
- 同一个问题被不同 Agent 重复解释。

### 3.2 后续可拆分为两个 Agent

当检索任务变复杂后，可以拆成以下两个角色。

#### 资料研究 Agent

- 理解用户问题涉及哪些命理主题。
- 将现代问题转换为古籍术语。
- 分别检索一级和二级资料。
- 找到相关原文、注解、例外和分歧。
- 发现证据不足时进行一次补充检索。
- 输出结构化证据包，不做最终结论。

#### 命理解读 Agent

- 读取后端命盘 JSON。
- 读取资料研究 Agent 提供的证据包。
- 结合命盘字段与文献进行解释。
- 区分命盘事实、传统解释和不确定性。
- 每个重要判断关联证据 ID。
- 不引用证据包之外的古籍内容。

两个 Agent 之间只能传递结构化 JSON，不进行无限制自由对话。

### 3.3 校验模块

校验模块初期使用程序实现，必要时再增加模型校验。它负责：

- 检查命盘字段有没有被修改。
- 检查回答中引用的证据 ID 是否存在。
- 检查引用文本是否与知识库一致。
- 检查一级原文和二级注解是否混淆。
- 检查是否出现无资料支持的确定性结论。
- 检查是否遗漏已检索到的重要流派分歧。
- 检查是否包含不适当的健康、法律或投资建议。

不建议将校验模块设计成另一个自由发挥的命理 Agent。

## 4. 知识库设计

知识库不是简单地把 PDF 放进向量数据库，而是由三个相互关联的层次组成。

### 4.1 原文库

保存书籍的原始文本和版本信息。

建议字段：

```text
work_id
书名
别名
作者或题署作者
成书年代
资料等级
版本名称
出版或刻印年代
卷
章节
页码或影像编号
原文
繁体原文
规范化文本
来源地址
版权状态
内容哈希
校对状态
```

原则：

- 原文不得被模型自动改写后覆盖。
- 不同版本分别保存。
- 作者归属存在争议时明确记录。
- OCR 文本必须标记校对状态。
- 不能把现代译文当成古籍原文。

### 4.2 注解与释义库

保存后世注解、现代释义和原文之间的关系。

建议字段：

```text
commentary_id
对应原文 passage_id
注解书名
注解者
注解年代
注解原文
现代释义
所属流派
解释主题
是否与其他注解冲突
审核状态
```

一段原文可以关联多个注解。例如：

```text
《滴天髓》正文
  |- 原注
  |- 任铁樵疏解
  `- 徐乐吾补注
```

检索和展示时不得把三者合并成一个作者的观点。

### 4.3 规则卡片库

把经过人工审核、能够参与推理的内容整理成结构化规则。

建议结构：

```text
rule_id
规则名称
主题
适用条件
结论
例外条件
前置规则
所属体系
证据 passage_id
支持注解 commentary_id
相反或不同规则
审核人
规则版本
状态
```

示例：

```text
规则名称：月令本气透干取格
主题：格局
适用条件：月令本气透出天干
结论：优先以该十神立格
例外：原局存在破格、变格或从格条件
所属体系：《子平真诠》
一级出处：对应原文 ID
二级解释：评注 ID
不同意见：《三命通会》相关段落 ID
```

规则卡片不是原文的替代，而是原文的结构化索引。

### 4.4 古今术语表

建立现代提问与古籍术语之间的映射。例如：

```text
性格 -> 性情、刚柔、清浊、精神
事业 -> 官星、印绶、格局、贵贱、职位
财富 -> 财星、食伤生财、财多身弱
婚姻 -> 妻财、夫星、夫妻、配偶宫
身体 -> 疾病、五行偏枯、寒暖燥湿
学习 -> 印星、文昌、学堂、词馆
```

术语表需要人工审核，不能完全由模型自动生成。

## 6. 文本处理方案

### 6.1 文本规范化

同时保留：

- 原始繁体文本。
- 规范化繁体文本。
- 简体检索文本。
- 现代释义。
- 搜索关键词。

规范化可以处理繁简转换、异体字映射、标点统一、空白换行、常见 OCR 错误，以及干支、十神、神煞等固定术语。原始文本必须保留，规范化文本只用于检索。

### 6.2 文本切分

不使用固定长度直接切割古文。建议按以下层级切分：

```text
书
  -> 卷
    -> 篇或章节
      -> 规则段落
        -> 原文句子
        -> 对应注解
```

每个最小片段应保留父级章节。检索命中一句原文时，最终返回应附带足够前后文，避免断章取义。

### 6.3 原文与注解对齐

优先使用人工审核的对齐关系：

```text
原文 passage_id
  -> 原注 commentary_id
  -> 任氏注 commentary_id
  -> 徐氏注 commentary_id
```

模型可以提出对齐建议，但不能未经审核直接写入正式知识库。

## 7. 检索方案

### 7.1 第一阶段不使用纯向量 RAG

先实现混合检索中的基础部分：

- 书名和作者过滤。
- 一级、二级资料过滤。
- 章节和主题过滤。
- 精确短语检索。
- 古今术语扩展。
- 字符级或词语级全文检索。
- 规则卡片检索。

对于古文，字符级二元或三元检索通常比完全依赖现代中文分词更稳定。

### 7.2 检索流程

```text
用户问题 + 命盘摘要
  -> 提取主题
  -> 古今术语扩展
  -> 一级资料召回
  -> 二级资料召回
  -> 规则卡片召回
  -> 合并去重
  -> 来源等级加权
  -> 相关性重排
  -> 补充父级上下文
  -> 标记冲突
  -> 证据包
```

一级资料优先不代表二级资料永远排在后面。二级资料可能更直接解释某段原文，但必须明确标注身份。

### 7.3 向量检索的加入条件

只有在测试证明以下问题明显存在时再加入向量检索：

- 现代提问无法召回对应古文。
- 同义词和隐含主题召回率不足。
- 术语表维护成本过高。
- 全文检索能够找到关键词，却无法找到相近概念。

加入后采用：

```text
关键词/BM25 召回
+ 向量召回
+ 元数据过滤
+ 重排模型
```

不采用纯向量结果直接交给 Agent。

### 7.4 证据包结构

```json
{
  "question": "用户问题",
  "topics": ["格局", "财星"],
  "chart_paths": [
    "chart.day_master",
    "chart.pillars.month"
  ],
  "evidence": [
    {
      "evidence_id": "ev_001",
      "level": "primary",
      "work": "子平真诠",
      "edition": "版本名称",
      "juan": "卷一",
      "section": "论用神",
      "quote": "古籍原文",
      "normalized_text": "规范化文本",
      "commentaries": ["ev_002"],
      "school": "子平",
      "score": 0.92
    }
  ],
  "rule_cards": [],
  "conflicts": [],
  "evidence_gaps": []
}
```

证据包不得提前生成完整命理结论。

## 8. 命理解读 Agent

### 8.1 输入

- 版本化命盘 JSON。
- 用户问题。
- 证据包。
- 对话摘要。
- 分析风格。
- 安全规则。

不向模型发送不必要的出生地点、真实姓名等敏感信息。

### 8.2 输出

建议使用结构化输出：

```json
{
  "summary": "整体说明",
  "chart_observations": [
    {
      "observation": "命盘事实",
      "chart_paths": ["chart.pillars.month"]
    }
  ],
  "interpretations": [
    {
      "claim": "传统命理解释",
      "evidence_ids": ["ev_001", "ev_002"],
      "school": "子平",
      "confidence": "medium",
      "limitations": []
    }
  ],
  "disagreements": [],
  "unanswered": [],
  "disclaimer": "传统文化解释说明"
}
```

### 8.3 Agent 约束

- 不修改四柱、大运、流年和流月。
- 不自行补造藏干、十神、神煞。
- 不声称引用未检索到的书籍。
- 不伪造古籍原文。
- 不把二级注解描述成原书原文。
- 不隐藏资料之间的明显冲突。
- 证据不足时明确说资料不足。
- 不提供确定性的疾病、寿命、投资或灾祸结论。

## 10. 版本管理

每次分析至少记录：

```text
chart_engine_version
calculation_policy_version
knowledge_corpus_version
rule_library_version
retrieval_version
embedding_model_version
reranker_version
model_provider

```

资料修改后生成新的知识库版本，旧分析继续关联旧版本，避免结果无法复现。

## 11. 测试与评估

### 11.1 知识库测试

- 原文和注解是否正确区分。
- 章节、卷和页码是否完整。
- OCR 是否存在关键术语错误。
- 繁简转换是否破坏专有词。
- 规则卡片是否有明确出处。
- 同一规则的不同版本是否被覆盖。

### 11.2 检索评测

建立人工标注问题集，覆盖：

- 格局。
- 旺衰。
- 调候。
- 用神。
- 十神。
- 神煞。
- 大运和流年。
- 婚姻、事业、财运与性情。
- 疾病相关的传统说法。
- 流派分歧。

评测指标：

- Recall@5、Recall@10。
- 证据命中率。
- 一级资料召回率。
- 错书率和错章节率。
- 注解错配率。
- 冲突资料召回率。

对比以下方案：

1. 关键词检索。
2. 向量检索。
3. 混合检索。
4. 混合检索加重排。

只有评测表明向量检索确有提升，才正式启用。

### 11.3 Agent 评测

- 命盘字段一致率。
- 引用真实性。
- 引用对结论的支持程度。
- 无证据结论比例。
- 一级与二级资料混淆率。
- 流派冲突披露率。
- 证据不足时的拒答能力。
- 相同命盘重复分析的稳定性。
- 高风险建议出现率。

### 11.4 回归测试

每次修改以下内容都运行完整评测：

- 知识库。
- 规则卡片。
- 提示词。
- 检索算法。
- 模型。
- 输出 Schema。

## 12. 数据安全和隐私

- 出生时间和地点不写入普通日志。
- 检索只使用推理所需的命盘字段。
- 模型请求中避免发送原始地点信息。
- 会话和分析支持删除。
- 模型提供商请求记录按最小数据原则处理。
- 知识库文本视为不可信输入，防止文档中的提示词注入。
- 资料导入必须检查版权和来源。
- 不允许运行时 Agent 自动抓取网络内容并直接加入正式知识库。

## 13. 实施阶段

### 阶段一：规则和资料规范

交付物：

- 一级、二级资料清单。
- 版本选择规则。
- 版权检查规则。
- 原文、注解和规则卡片 Schema。
- 命理主题词表。
- 资料引用格式。

验收条件：任意一段内容都能说明来自哪本书、哪个版本和哪一章，原文与注解不会混淆。

### 阶段二：知识库基础

交付物：

- PostgreSQL 数据表。
- 原始文件存储。
- 资料导入工具。
- 文本规范化工具。
- 章节切分工具。
- 人工审核状态流转。
- 知识库版本管理。

验收条件：可以导入一本一级资料及其二级注解，并按书名、章节和主题查询。

### 阶段三：基础检索

交付物：

- 精确短语检索。
- 字符级全文检索。
- 元数据过滤。
- 古今术语扩展。
- 一级、二级双路召回。
- 证据包生成。
- 检索评测集。

验收条件：典型问题能够召回正确原文及对应注解，返回结果包含完整出处。

### 阶段四：单 Agent 垂直切片

交付物：

- 模型 Provider Adapter。
- 版本化提示词。
- 结构化分析输出。
- 引用展示。
- SSE 流式返回。
- 基于同一命盘的连续追问。

验收条件：Agent 不修改命盘，每项核心解释至少有一条证据，无证据时能够说明不足。

### 阶段五：校验和质量控制

交付物：

- 命盘一致性校验。
- 引用存在性校验。
- 原文精确匹配校验。
- 资料等级校验。
- 冲突遗漏检测。
- Agent 回归评测。

验收条件：伪造引用能够被拦截，二级注解不能被标成一级原文。

### 阶段六：向量检索实验

交付物：

- 古文与现代释义向量索引。
- 混合召回。
- 重排器。
- 与基础检索的对比报告。

验收条件：向量方案在评测集上有明确提升，并且不显著增加错书、错段和流派混淆。

### 阶段七：可选双 Agent 编排

仅在以下情况出现后实施：

- 查询规划明显复杂。
- 一次检索经常无法获得足够证据。
- 命理解读 Agent 同时负责检索和分析导致稳定性下降。
- 资料分歧需要独立研究步骤。

交付物：

- 资料研究 Agent。
- 结构化证据交接协议。
- 一次补充检索机制。
- 循环次数和成本限制。

## 14. MVP 完成标准

满足以下条件才视为 Agent MVP 完成：

- 使用确定性命盘 JSON，不由模型计算四柱。
- 能从一级和二级资料中检索相关内容。
- 原文、注解、规则卡片能够相互追溯。
- 核心解释带有书名、章节和证据。
- 不同流派存在冲突时明确提示。
- 不伪造书名、作者和古籍原文。
- 检索和分析都有自动化评测。
- 模型、提示词、资料库和规则库全部版本化。
- 支持流式分析、失败重试和连续追问。
- 敏感出生资料不进入普通日志。
- 用户能够删除分析和对话数据。

## 15. 最终建议

先建设知识库和基础混合检索，再完成单 Agent 垂直切片；校验体系稳定后，依据评测结果决定是否增加向量检索和资料研究 Agent。不要在资料、引用和评测基础尚未建立时直接进入复杂多 Agent 编排。
